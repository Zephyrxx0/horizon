## Tech Debt (Non-Blocking)

No critical blockers. 3 warning-level architecture observations from the integration checker:

### 1. `TrackingModal` Dual-Mount Pattern
**Phase:** 5 | **Severity:** WARNING  
`TrackingModal` is mounted twice — globally in `App.tsx` (header Track button) and locally in `IdentityStep.tsx` (duplicate passport handoff). Both instances work correctly and serve different call sites. If `TrackingModal` ever holds mutable state that needs to sync across instances, the dual-mount could cause stale state. Currently harmless as each mount is ephemeral.  
**Recommendation:** Track for Phase 6 — if modal gains shared state, consolidate into a single global mount with a ref prop for pre-filled values.

### 2. `ConfirmationScreen` Receipt Type Cast
**Phase:** 5 | **Severity:** WARNING  
`ConfirmationScreen.tsx` accesses receipt via `(context as unknown as { receipt?: PaymentReceiptData }).receipt` alongside `answers.receipt`. The `as unknown as` escape hatch signals a schema ambiguity in where the receipt field lands in machine context.  
**Recommendation:** Extend `WizardContext` type to include `receipt?: PaymentReceiptData` directly, eliminating the cast.

### 3. Legacy Demo Step Handlers in `selectors.ts`
**Phase:** 1 | **Severity:** LOW  
`selectors.ts` carries backward-compatible handlers for legacy demo step IDs (`trip`, `dependent`, `review`) from the development prototype. These are isolated and don't affect the production journey topology, but they're dead paths in the shipped UX.  
**Recommendation:** Remove in a Phase 6 cleanup pass.
